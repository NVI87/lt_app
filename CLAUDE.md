# CLAUDE.md

## Git workflow

Работай в текущей git-ветке, в которой была запущена сессия.

Не переключай и не создавай ветки.
Не выполняй merge, rebase, push или commit без моего явного запроса.
Не изменяй файлы вне текущего репозитория.

## Working mode

- Сначала изучай существующий код и контекст репозитория.
- Для обычных изменений действуй самостоятельно.
- Перед удалением, массовым перемещением файлов, изменением публичных
  контрактов, секретов, инфраструктуры или внешних данных — сначала спроси.
- Не создавай абстракции, тесты, документацию и новые подсистемы без
  практической причины, видимой в текущей задаче.
- После работы кратко перечисляй сделанные изменения и способ проверки.

## Назначение проекта

`lt_app` — инструмент нагрузочного тестирования внешнего ETL-сервиса.

Система должна воспроизводить события из CSV-дампа в тестовый Kafka-topic, ограничивать скорость публикации по lag consumer group тестируемого ETL, собирать диагностические артефакты и строить итоговую статистику по тестовой сессии.

Актуальная бизнес-цель: получить Streamlit MVP для одной управляемой тестовой сессии с Start/Stop, прогрессом, артефактами и итоговым отчётом.

## Главный принцип работы

Пользователь владеет доменным контекстом, архитектурой и правом принимать решения. Claude Code — точечный pair-programming инструмент, а не автономный исследователь кодовой базы.

Работай по циклу:

1. Получи одну конкретную задачу.
2. Прочитай только явно разрешённые файлы.
3. Дай короткий план: цель, файлы, риски, проверки.
4. Ничего не меняй до явного подтверждения пользователя.
5. После подтверждения сделай минимальный согласованный набор изменений.
6. Покажи изменённые файлы, команды проверок и их результат.
7. Не делай commit, push, PR, создание ветки или изменение зависимостей без отдельного прямого указания.

Не заменяй конкретную задачу пользователя «полезной» самостоятельной инициативой.

## Критические ограничения

### Агентный режим и стоимость

Никогда не запускай:

- `Explore`;
- `Plan`;
- subagents;
- background agents;
- agent teams;
- параллельные задачи;
- рекурсивное исследование репозитория;
- широкие поисковые запросы вроде «изучи кодобазу», «найди все проблемы» или «проанализируй архитектуру».

Не предлагай и не запускай эти механизмы, даже если задача сформулирована широко. Claude Code уже использовался для неограниченного Explore-анализа и создал неприемлемый расход токенов без полезного соразмерного результата.

Работай только в основном чате, последовательно и по одному небольшому шагу.

### Защита данных

Не читай содержимое и не выводи в чат, логи, diff или ответ:

- `err_events/`;
- `artifacts/`;
- `data/`, `datasets/`, `fixtures/`, `samples/`, `examples/`;
- CSV/JSON/JSONL/XML с рабочими событиями и примерами payload;
- PDF, DOCX, XLSX, изображения, архивы;
- `.env`, секреты, сертификаты, private keys;
- `.git/`, `node_modules/`, `.venv/`, `venv/`, `dist/`, `build/`, `coverage/`, `logs/`, `tmp/`.

Исключение возможно только при отдельной явной команде пользователя, содержащей точный путь и цель чтения.

Не выводи целиком Kafka payload, JSON-отчёты ETL, содержимое дампов, credentials или большие фрагменты данных. Для progress/UI допустимы только metadata и агрегаты.

### Git и внешнее состояние

Без явного указания пользователя запрещено:

- создавать, удалять, перемещать или переименовывать файлы;
- выполнять команды, меняющие environment;
- выполнять миграции, обращения к production, деплой;
- делать `git add`, commit, push, reset, rebase, force push;
- менять зависимости, lock-файлы, конфигурацию CI;
- удалять тестовые артефакты, CSV, JSON или каталоги.

После явного разрешения на изменение сначала покажи планируемые файлы и причину каждого изменения.

Разрешено:

## Целевая архитектура

```text
Streamlit UI
    │
    ▼
Session supervisor / worker process
    ├── Kafka event generator
    ├── OpenSearch index monitor
    ├── Kafka JSON artifact collector
    ├── ETL report statistics builder
    └── ETL statistics projection builder
```

### Границы слоёв

- `app.py`: Streamlit UI. Форма конфигурации, Start/Stop, отображение status/progress/error, YAML import/export, скачивание артефактов. Не содержит Kafka/OpenSearch/аналитическую бизнес-логику.
- `worker.py`: lifecycle одной тестовой сессии. Запускает async-задачи, получает stop signal, передаёт компактные события в UI, завершает и запускает post-processing.
- Модули Kafka/OpenSearch/аналитики: изолированная предметная логика без Streamlit, CLI, `argparse`, `__main__` и multiprocessing orchestration.
- Один worker-процесс соответствует одной тестовой сессии. Несколько независимых Kafka-конфигураций в будущем запускаются отдельными worker-процессами.

### Конфигурация

Конфигурация разделена на два уровня:

- YAML: не-секретные session settings, которые пользователь редактирует в Streamlit и может экспортировать/импортировать.
- environment или локальный `.env`: пароли, SASL credentials, TLS paths, приватные endpoints и иные секреты.

Используй Python 3.11+, Pydantic v2 и `pydantic-settings`.

Модульные settings classes:

- `KafkaEventGeneratorSettings`, prefix `KAFKA_EVENT_GENERATOR_`;
- `OpenSearchIndexMonitorSettings`, prefix `OPENSEARCH_INDEX_MONITOR_`;
- `KafkaArtifactCollectorSettings`, prefix `KAFKA_ARTIFACT_COLLECTOR_`;
- `EtlReportStatisticsSettings`, prefix `ETL_REPORT_STATISTICS_`;
- `EtlStatisticsProjectionSettings`, prefix `ETL_STATISTICS_PROJECTION_`.

Supervisor создаёт и передаёт settings modules. Не добавляй секреты в YAML, `.env.example`, README, исходники, логи или Git.

### Артефакты

Артефакты одной сессии должны изолироваться по session id:

```text
artifacts/<session_id>/
├── session.json
├── index_counts.csv
├── err_events/
├── stats_done.csv
├── stats_skipped.csv
├── stats_read_failures.csv
├── coefficients.csv
├── projection_by_stage.csv
├── projection_total.csv
└── report.md
```

Не записывай большие файлы в корень репозитория. Не удаляй артефакты автоматически.

## Контракты модулей

### Kafka event generator

Назначение: читать CSV-дамп Kafka-событий и публиковать их в test topic.

Инварианты:

- CSV содержит `offset`, `timestamp`, `partition`, `key`, `value`.
- `value` передаётся в Kafka как исходные bytes. Не декодируй, не меняй и не пересобирай payload через `json.dumps`.
- Lag измеряется для consumer group тестируемого ETL-сервиса.
- При достижении лимита lag генератор приостанавливает публикацию и ждёт снижения lag.
- `max_messages` — суммарный лимит отправок.
- `repeat_source=true` циклически повторяет короткий CSV до достижения `max_messages`.
- Kafka errors и ошибки чтения CSV не проглатываются: supervisor должен получить failed result.
- Progress event содержит metadata, счётчики и lag, но не полный payload.

### OpenSearch index monitor

Назначение: периодически получать document count заданных OpenSearch-индексов и писать CSV-артефакт.

Инварианты:

- `opensearch-py` синхронный; сетевые запросы не должны блокировать asyncio event loop.
- Ошибка count одного индекса записывается как error record, но не останавливает остальные индексы.
- CSV содержит `timestamp`, `index_name`, `document_count`, `error`.
- Для закрытого тестового контура допустимы `verify_certs=false` и `ssl_assert_hostname=false`, если это явно задано в settings.
- Callback UI не должен ломать monitor.

### Kafka JSON artifact collector

Назначение: читать Kafka debug/error topic ETL и сохранять каждое JSON-сообщение отдельным файлом.

Инварианты:

- Topic содержит и ошибки, и потенциально крупные отчёты успешной обработки.
- Имя файла строится из `topic-partition-offset`.
- Запись атомарная: временный файл в той же директории, затем `os.replace`.
- Offset коммитится только после успешной файловой записи.
- Commit конкретного record использует `message.offset + 1`.
- Consumer должен проверять stop event по timeout и не зависать в бесконечном `async for`.
- JSON decoding и файловая запись не блокируют event loop.
- Ошибка JSON decoding или файловой записи не должна коммитить сообщение.
- UI получает только metadata: topic, partition, offset, путь, количество файлов.
- Для отдельной тестовой сессии обычно используется уникальный collector group id.

### ETL report statistics builder

Назначение: преобразовать JSON-артефакты одной сессии в табличную статистику.

Инварианты:

- В DONE-таблицу включаются только `DONE` и `SUB_DONE`.
- Извлекаются stage metrics: `wall_time_sec`, `cpu_mean_pct`, `cpu_peak_pct`, `rss_mean`, `rss_peak`, `samples`.
- Не-DONE, отсутствующие stats и неполные вложения попадают в skipped CSV.
- Ошибки чтения и JSON parsing попадают в отдельный read failures CSV.
- CSV создаются даже при пустом результате и имеют фиксированные заголовки.
- Ошибка одного JSON не останавливает обработку остальных файлов.
- JSON parsing, pandas и файловая запись не блокируют event loop.

### ETL statistics projection builder

Назначение: построить регрессионные коэффициенты и прогнозы по `stats_done.csv`.

Инварианты:

- Модели строятся для каждой пары `(attach_type, stage)`.
- Time model: `wall_time_sec = slope * size_mb + intercept`.
- Memory model: `rss_peak_bytes = slope * size_mb + intercept`.
- Для normal least-squares model рассчитывается R².
- При одном наблюдении или одинаковых размерах допускается только явно помеченный fallback `y = slope * x`.
- Прогноз вне observed training range обязан иметь `extrapolated=true`.
- Суммарное время — сумма stage time; итоговый RSS — максимум stage peak RSS, не сумма.
- Создаются `coefficients.csv`, `projection_by_stage.csv`, `projection_total.csv`.

## Стандарты кода

- Python 3.11+.
- Полные type annotations для всех публичных и приватных классов, dataclass, функций, методов и coroutine.
- Docstrings для всех классов, dataclass, функций, методов и coroutine в Sphinx native / reStructuredText формате с `:param:`, `:returns:`, `:raises:`, `:ivar:` там, где применимо.
- Dataclass и enum использовать для событий, результатов, режимов и компактных межслойных контрактов.
- Избегать глобальных mutable settings и хардкодов infrastructure values.
- Логи должны содержать metadata и identifiers, но не payload, secrets или большие объекты.
- Ошибки, которые меняют исход тестовой сессии, должны доходить до supervisor-а. Не подавляй их ради продолжения работы без явной политики обработки.
- Callback/UI errors могут логироваться и не должны останавливать worker-модули.
- До добавления новой зависимости объясни, зачем она нужна; не меняй зависимости без отдельного разрешения.

После реализации и только при разрешении пользователя:
